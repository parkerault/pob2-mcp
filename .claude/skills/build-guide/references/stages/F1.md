# F1: the endgame-only build's final compile (`build-guide-coordinator`)

A fresh coordinator step after the design gate's `accept` or `accept:file` (D-413): it checks that the plan is the
one the user accepted, compiles it measure-only, and runs the final compile, the build's only write into the
builds folder, in the same step. It writes its verdict file in the D2 gate's shape. The D2 gate stays the final
compile of a build with its campaign, and runs only after D2. You check; you don't design. Fix nothing in the
plan: a failure is a fault, routed below.

## Inputs

- **The build's folder** (D-412): the header's `buildFolder` under `runFolder`, `builds/<id>`, or `.` for a run
  migrated from schema 3. `plan.json` and `compile-record.json` are there, and `<plan>` is
  `<runFolderRel>/<buildFolder>/plan.json` (`<runFolderRel>/plan.json` when `buildFolder` is `.`).
- **Header:** `stage: "F1"`, `attempt` (counts this concept's F1 attempts), `concept`, `mode`, `runFolder`,
  `runFolderRel`, `buildFolder`, `compile: "final"`, `buildName`, `accepted` (the findings the user accepted at a
  D1 gate escalation, option 1, or at an earlier F1 escalation: F1 doesn't count them as failures), `writes`: the
  verdict file `reports/gates/F1-<concept>-a<attempt>.json` (at the run folder's root).
- **`buildName`**, as the runner builds it by the run checker's PoB file name rule: `<slug>-<YYYY-MM-DD>-<n>-<card
  id>`, the run folder's last two segments and the card id joined with `-` (D-412), so two builds of one run
  never share a file; for a build in `.` (a migrated run's), `<slug>-<YYYY-MM-DD>-<n>`, with no card id. Use it as
  given: never pick another.
- **Prompt:** the passing D1 gate's verdict file, `reports/gates/D1-gate-<concept>-a<n>.json`.
- **Read**, before any compile: that verdict file's `planSha1`, the sha1 of the plan the gate compiled, which the
  user accepted at the design gate. A verdict file without one (a D1 gate from before amendment 9): Grep
  `compile-record.json` for `"planSha1"` and `"mode"` now, before you compile; its `planSha1` is the gate's when
  its `mode` is `measure-only` (no compile ran since the gate). After each compile, `mcp__pob2__compile_plan`'s
  text: each stage's line with its V1 and V2 verdict, and every V1 and V2 finding up to 200; when a line says how
  many more, Grep `compile-record.json`'s `stages.<id>.v1.findings` and `stages.<id>.v2.findings` for them.
  Never Read the record whole.

## Work

1. **The check compile.** Compile the whole plan measure-only: `mcp__pob2__compile_plan {plan_path: "<plan>",
   measure_only: true}`, with no `stages`. A compile error is part `compiled` failing (code `compile-error`, the
   error line as the message, the plan stage it names as `stage`); then `v1` and `v2` are `unverified`, and you
   write the verdict file.
2. **The sha1 check.** Grep the new `compile-record.json` for `"planSha1"`: the plan's sha1 now. When it isn't
   the gate's, the plan changed since the user accepted it: part `compiled` fails, code `plan-changed`, the
   message both sha1s; `v1` and `v2` are `unverified`, no final compile runs, and you write the verdict file.
3. For every stage in `stagesCompiled`, each finding of its `v1` and `v2` verdicts becomes a gate finding: part
   `v1` or `v2`, the record's `code` unchanged, the plan stage as `stage`, the record's message. A part with any
   finding is `fail`. One equal to a finding in the header's `accepted` (same plan stage, part and code) is
   reported with `"accepted": true`, and fails no part.
4. **The final compile**, only when the compile, the sha1, V1 and V2 pass (accepted findings aside): call
   `mcp__pob2__compile_plan {plan_path: "<plan>", build_name: "<the header's buildName>"}` exactly once: the whole
   plan, not measure-only. It writes the PoB file into the builds folder through the server (C-17), and
   `compile-record.json` with `importCode` and the PoB file's path (D-205).
5. **A refusal by the write ledger** (D-211: C-17's "already exists" or changed-on-disk wording) is part `compiled`
   failing with code `ledger-refused`, the error lines verbatim; any other error of the final compile, code
   `final-compile`. Never retry it, never pick another `build_name`, and never work around it. On success, the new
   record's `v1` and `v2` verdicts over every stage are the verdict's, as in step 3.

**Routes** (the runner's, `gates.md`): a pass renders `audit.md` (`render-audit.mjs <runFolder> --build <id>`),
then W1, or ends the build `file-only` after `accept:file`. A plan changed since the gate, a V1 or V2 failure not
in `accepted`, or a compile error on the plan the gate passed is a fault, not a design finding: F1 re-runs once,
uncounted, and a second failure escalates. A `ledger-refused` escalates at once, since no retry changes it.

**The escalation** (stage `F1`, the verdict file above): 1. **accept**, not after a compile failure or a ledger
refusal: the failing findings join `accepted`, and F1 runs once more, uncounted; 2. **guidance and one more
retry**: D1 (D1-build, D1-tree and D1-finish as the guidance needs), the D1 gate, and the design gate again, since
the build changed; then F1; 3. **back to the verification gate**: the build ends `dropped`; 4. **stop**: the build
ends `escalated`. For a ledger refusal, the user can also restore or remove the changed file and answer 1, which
retries F1 and accepts no finding.

## Writes

The verdict file `reports/gates/F1-<concept>-a<attempt>.json`, and nothing else: the server writes the record,
the XML and the PoB file. Its shape is the D2 gate's (`gates.md`), with `stage: "F1"`:

```json
{
  "stage": "F1",
  "concept": "r1-a-2",
  "attempt": 1,
  "verdict": { "compiled": "pass", "v1": "pass", "v2": "pass" },
  "findings": [],
  "planSha1": "4f0c3b9e1d2a7c6b5e8f9a0b1c2d3e4f5a6b7c8d",
  "finalCompile": { "compiled": true, "errors": [], "recordPath": "builds/r1-a-2/compile-record.json", "pobFile": "titan-blood-hunt-2026-10-08-1-r1-a-2.xml" }
}
```

- `verdict`: each part `pass`, `fail` or `unverified`; `findings`: `{part, code, stage, message, accepted?}`.
- `planSha1`: the D1 gate's, the plan the user accepted.
- `finalCompile`, when step 4 ran: `compiled`, whether it succeeded; `errors`, its error lines verbatim;
  `recordPath`, the record from `runFolder`; `pobFile`, the new record's `pobFile.path`, or `null` when it failed.
  Don't copy the import code: `compile-record.json` is its one home, and W1 copies it from there (D-260).

## Returns

At most 8 lines: the verdict in one line, the verdict file, and the PoB file when the final compile wrote it.

```
F1 r1-a-2 attempt 1: compiled pass, v1 pass, v2 pass; final compile written
reports/gates/F1-r1-a-2-a1.json
titan-blood-hunt-2026-10-08-1-r1-a-2.xml
```

## Fault directives

None.
