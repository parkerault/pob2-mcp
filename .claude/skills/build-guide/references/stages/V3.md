# V3: provenance, every claim tagged (`build-guide-provenance`)

Slice 03 §5.3 step 6, §7.3 and §7.4; spine C-30, C-36, D-105, D-232, D-237. V3 checks that every claim in
`plan.json`, `dossier.md` and `guide.md` shows its source in a well-formed tag or citation (C-36: "no
untagged claim"). It doesn't judge whether a claim is true: the three V4 lenses do that (`V4.md`). It runs
beside them, at most 3 agents in flight, once per verification pass.

## Inputs

- **Header:** `stage: "V3"`, `attempt`, `concept` (the concept the guide is for), `pass` (the verification
  round, from 1), `mode`, `runFolder`, `runFolderRel`, `compile: "none"`, `writes: []`, and:
  - `findings`: empty on a pass's first attempt; on a re-run, why the earlier attempt of this pass couldn't
    be used (`null-result`, or `unusable-report` naming a field or a count). Never text from the artifacts;
  - `accepted`: V3 findings the user accepted at an escalation, by `id`, `artifact` and `location` only
    (D-253). Report the same issue at the same location under the same `id`; the workflow and the run
    checker then count it as accepted.
- **Read** (paths relative to `runFolder`):
  - `plan.json`: every `stages[].claims[]` entry, the `ledger[]` and `prices[]` ids, which stages have a
    `variant`;
  - `dossier.md` and `guide.md`: every marker `[^<id>]` and every definition line;
  - `run-log.json` (its `mode`);
  - every concept skeleton, `concepts/<id>/plan.json`: the dossier's citations resolve against any plan of
    the run;
  - the committed C1/E1 files a `data` citation names, under `data/` (`data/campaign/`, `data/enemies/`);
  - `.claude/skills/build-guide/references/source-markers.md` (the tag forms, the citations, the counting
    rules, the report shape) and `docs/build-guide/plan-reference.md` (the plan's claim fields).

## Work

1. **Count the claims** exactly as `source-markers.md` counts them, because the run checker recounts them
   and fails a report whose coverage differs (FR-W7):
   - `plan`: one per `stages[].claims[]` entry of `plan.json` (not the ledger inputs, not the scenario
     tags, not the concept skeletons);
   - `dossier` and `guide`: one per definition line `[^<id>]: …` of that file (not per marker).
2. **Check each plan claim.** Its `source` is a tag object `{kind, ref, accessed?, patch?, confidence?}` or
   a citation string:
   - `kind` is one of C-30's five; `ref` is non-empty and in its kind's form: `pob-computed`, a record field
     (`<stageId>.<Field>` or `<stageId>.g<group>s<skill>p<statSet>.<Field>`); `pob-data`, a pinned PoB
     `file:line` or a lookup-tool result; `external`, an `http(s)` URL with `accessed` (YYYY-MM-DD) and a
     `confidence`; `judgment`, the reasoning in a few words with a `confidence`; `external-unavailable`,
     exactly `external source unavailable (offline run)` with a `confidence`;
   - `confidence` is `H`, `M` or `L`;
   - `ledger:<id>` names an entry of `plan.json`'s `ledger[]`; `price:<id>` an entry of its `prices[]`
     (D-237); `data:<file>#<key>` a fact in `data/<file>`'s `facts`, `<key>` optionally ending in
     `[<member>]` that the fact's value has (D-232).
3. **Check each markdown claim**, in `dossier.md` and `guide.md`:
   - every marker has **exactly one** definition line, and every definition sits under the file's last
     heading (`Sources` in the guide), with nothing after them;
   - each definition parses as one of `<kind> | <ref> [| accessed: YYYY-MM-DD] [| patch: <p>] [| confidence:
     H|M|L]`, `ledger | <id>`, `data | <file>#<key>` or `price | <id>`, with the same rules as step 2;
   - in `guide.md`, a `ledger` or `price` definition resolves against `plan.json`; in the dossier, against
     any plan of the run (the concept skeletons included);
   - **untagged claims**: every number the guide or the dossier takes from the record, a ledger entry, a
     price or a C1/E1 fact, and every statement of how a game mechanic works, carries a marker. Headings
     (the loadout names), the fenced import code and the template's fixed wording are exempt. A sentence
     that needs a marker and has none is a finding.
4. **Mode** (C-30). In an online run (`run-log.json`'s `mode`), an `external-unavailable` tag anywhere is a
   finding: online, the claim needs a real source. In an offline run it is a well-formed tag, and V4's
   `sources` lens accounts for it.
5. **Findings.** One per problem: `id` (`v3-1`, `v3-2`, …, or the `id` the header's `accepted` gives that
   issue at that location), `artifact` (`plan.json`, `dossier.md` or `guide.md`), `location`
   (`stages[<i>].claims[<k>]`; `<file> [^<id>]` for a definition; `<H2 title>, line <n>` for an untagged
   sentence, its line in the file. A location never quotes the artifact: it may travel to later passes'
   verifiers, R-5), `claim` (the claim's text, or its definition line), `issue` (what is
   wrong, in a few words), `evidence` (the rule it breaks), `owner` and `status: "unresolved"`. The
   **owner** is the step that wrote the claim (slice 03 §5.5):

   | Finding is in | `owner` |
   |---|---|
   | `guide.md` | `W1` |
   | an endgame stage of `plan.json` (one with a `variant`), a ledger entry citing one, an endgame price | `D1` |
   | a campaign stage of `plan.json`, or a ledger entry citing only campaign stages | `D2` |
   | `dossier.md` | `dossier-fix` |

## Writes

Nothing. You have no write tool: the report is your return, and the skill writes it to
`reports/v3-<concept>-p<pass>.json` unchanged (R-5).

## Returns

Your last message is this JSON and nothing after it:

```json
{
  "stage": "V3",
  "concept": "c1",
  "pass": 1,
  "mode": "offline",
  "coverage": { "plan": 12, "dossier": 4, "guide": 12 },
  "findings": [
    { "id": "v3-1", "artifact": "guide.md", "location": "guide.md [^g9]",
      "claim": "[^g9]: external | https://maxroll.gg/poe2/… | patch: 0.5.5",
      "issue": "external tag without accessed or confidence", "evidence": "C-30: external needs accessed and confidence",
      "owner": "W1", "status": "unresolved" }
  ],
  "verdict": "fail"
}
```

- `stage` `"V3"`, no `lens`; `concept` and `pass` from the header; `mode` the run log's.
- `coverage` is `{plan, dossier, guide}`: the claims counted in step 1, each equal to the run checker's
  count.
- `verdict` is `pass` exactly when no finding is `unresolved`. V3 reports nothing `accepted-offline`.

## Fault directives

None.
