# V4: claims are true, one lens each (`build-guide-verifier`)

Slice 03 §5.3 step 6, §7.4; spine C-30, C-33, C-36, D-106, D-122, D-142, D-164, D-179, D-219, D-232, D-234,
D-237, D-254, A-29, A-P11. Three verifier agents check that the claims of `plan.json`, `dossier.md` and
`guide.md` are true, one per lens: `ledger`, `sources` and `prose`. None of them wrote anything it checks,
and none can change it (D-142). With V3 (`V3.md`) they run at most 3 in flight, once per verification pass;
the guide passes only when no finding is `unresolved` (D-179).

## Inputs

- **Header:** `stage: "V4"`, `lens` (your job), `attempt`, `concept` (the concept the guide is for),
  `pass`, `mode`, `runFolder`, `runFolderRel`, `compile: "none"`, `writes: []`, and:
  - `findings`: empty on a pass's first attempt; on a re-run, why the earlier attempt of this pass couldn't
    be used (`null-result`, or `unusable-report` naming a field or a count). Never text from the artifacts;
  - `accepted`: V4 findings the user accepted at an escalation, by `id`, `artifact` and `location` only
    (D-253). Report the same issue at the same location under the same `id`.
    An accepted finding covers only the **same** finding: the same `id`, `artifact` and `location` (a
    `<H2 title>, line <n>` location by its section). **Never give an accepted `id` to another issue**:
    number your new findings after the highest accepted id of yours (`v4-<lens>-3` accepted, so new ones
    start at `v4-<lens>-4`).
- **Read** (paths relative to `runFolder`):
  - `plan.json` (stages, `claims`, `config.scenario`, `ledger`, `prices`), `compile-record.json` (the final
    compile's record, C-33: each stage's `outputs`, `skillOutputs` and `loadoutName`, and the `ledger`
    values), `dossier.md`, `guide.md`, `run-log.json` (`mode`);
  - the committed C1/E1 files under `data/` that a claim, a scenario entry or a ledger input cites
    (`data/campaign/`, `data/enemies/`), each fact with its `value`, `source` (an id in the file's
    `sources[]`), `patch` and `confidence`;
  - `.claude/skills/build-guide/references/source-markers.md` (tags, citations, counting, the report),
    `.claude/skills/build-guide/references/lookups.md` (the lookup tools and `check_model_coverage`'s
    statuses), `.claude/skills/build-guide/references/gates.md` (the floor, budget and rolled-skill rules)
    and `docs/build-guide/plan-reference.md` (the ledger formula grammar and the plan's fields).

## Work: every lens

- **Lookups** (L, D-231): `lookup_game_data`, `check_model_coverage`, `search_tree_nodes`, `list_gems`,
  `get_classes`, as `lookups.md` says:
  - a unique's full text comes only when the lookup returns exactly one unique: look it up by its exact
    name (D-239);
  - `{mode: "mechanic", query, kind}` lists one kind only (`gem`, `unique`, `passive`, `mod`) when a broad
    query fills every slot with another (D-240);
  - a gem's stat sets show their base attack damage and base critical hit chance (D-241).
- **What PoB applies.** A **partly parsed** line means PoB applies **none** of it; an unparsed line is
  ignored. A PoB number (`pob-computed`) that relies on such a line is wrong, and the ledger must
  hand-calculate the whole line (D-106). **`possibly unread` is advisory** (D-243): the coordinator
  confirms it by a measurement (two stages compiled measure-only). You can't compile: when a number rests
  on a `possibly unread` line and neither the plan's claims nor the dossier record that measurement,
  report a finding for the claim's owner ("possibly unread, not confirmed by measurement"); never guess the
  number yourself.
- **Offline and online** (C-30, D-201). Read the mode from `run-log.json`. In an offline run you open no
  URL at all. A claim tagged `external-unavailable` is reported by the `sources` lens: `accepted-offline` in
  an offline run, `unresolved` in an online one.
- **Grounding confidence** (A-29). A value the grounding rates M or L (a waystone modifier's size, the
  interlude +8, the 65+/75+ trial dispute, the Martyr point) is used as recorded; a finding whose check
  rests on one says so in its `evidence`.
- **Findings.** One per false or unsupported claim: `id` (`v4-<lens>-1`, …, or the `id` the header's
  `accepted` gives that issue at that location), `artifact`, `location` (`stages[<i>].claims[<k>]`,
  `ledger[<i>] (<id>)`, `stages[<i>].config.scenario[<k>]`, `prices[<i>] (<id>)`, `<file> [^<id>]`, or
  `<H2 title>, line <n>`, the sentence's line in the file; a location never quotes the artifact, since it
  may travel to later passes' verifiers, R-5), `claim` (its text), `issue`, `evidence` (what you
  re-derived or looked up, with the numbers), `owner` and `status`. The **owner** is the step that wrote
  the claim (slice 03 §5.5): `W1` for `guide.md`; `D1` for an endgame stage (one with a `variant`), a
  ledger entry citing one (or citing no stage), an endgame price; `D2` for a campaign stage or a ledger
  entry citing only campaign stages; `dossier-fix` for `dossier.md`. A guide number that differs from a
  right record or ledger value is `W1`'s; a wrong ledger entry is its writer's, even when the guide copied
  it faithfully.

## Lens `ledger`: re-derive every ledger entry (D-179, C-33, D-254)

1. For **every** entry of `plan.json`'s `ledger[]`, evaluate its `formula` yourself, by
   `plan-reference.md`'s grammar: each one-segment name is an input of the entry (its `value`), each
   `<stageId>.<Field>` is that stage's `outputs` field in `compile-record.json`, each
   `<stageId>.g<group>s<skill>p<statSet>.<Field>` its `skillOutputs` field. Check each input's value
   against its tag's source: a `pob-data` input with a lookup, a value copied from a C1/E1 fact against
   that fact (the tag names it). Compare the result with the record's value for the entry (equal to 2
   decimals); a mismatch, a formula that doesn't say what the entry's `claim` says, or a missing record
   value is a finding naming the entry's `id`.
2. **The reference hits** (D-119, D-254; a derived scenario value is V4's to re-derive, A-P11). For every
   endgame stage (`variant` set), re-derive the five waystone-scaled hits from the facts themselves, not
   only from the entry's inputs:
   - the area level: the budget variant's is `enemies/waystones.json#area-level.offset` plus 15 (T15); the
     non-budget variant's is `enemies/waystones.json#area-level.max`;
   - `base` = `enemies/map-monsters.json#damage.by-level[<area level>]`; `increased` = the `max` of
     `enemies/waystones.json#mods.increased-monster-damage`; `extra` = the `max` of
     `enemies/waystones.json#mods.extra-damage-as-element` (both confidence M, A-29);
   - physical = `base × (1 + increased / 100)`; fire, cold, lightning and chaos each =
     `base × (1 + increased / 100) × extra / 100`.

   Each of the five must exist as the ledger entry `hit_<stage id>_<type>` (`hit_b_physical`,
   `hit_n_chaos`), with those inputs and that formula, its record value equal to your hit, and the stage's
   `config.scenario` entry `enemy<Type>Damage` (`enemyPhysicalDamage`, `enemyFireDamage`, …) equal to it
   rounded to 2 decimals. A missing entry or scenario hit, or any mismatch, is a finding (owner `D1`).
3. For every guide number that cites an entry (a `ledger | <id>` definition), compare it with the record's
   value for that entry, as the guide rounds it; a mismatch is a `W1` finding.
4. **Coverage** `{entries, rederived}`: `entries` is the number of entries in `plan.json`'s `ledger[]`;
   `rederived` how many you re-derived, which must equal `entries` (D-179).

## Lens `sources`: every source opened, every data and price claim checked (D-179, D-232, D-237)

Count the claims as `source-markers.md` does, over `plan.json`, `dossier.md` and `guide.md` together;
"endgame" means the guide's two `Endgame:` H2s (the section of a definition's first marker) and the plan's
`variant` stages, and everything else, the whole dossier included, is "elsewhere". Then:

1. **`external`** claims: online, open **every** source with WebFetch, only on D-171's hosts (poe2db.tw,
   maxroll.gg, game8.co, poe-vault.com, patch-note mirrors; never pathofexile.com or poe.ninja; a URL on
   another host is a finding, not a fetch), and check that it says what the claim says, for the patch the
   tag names. Offline, open nothing: an `external` claim in an offline run is an `unresolved` finding (it
   should be `external-unavailable`), and `opened` is 0.
2. **`data`** claims (`data:<file>#<key>` in the plan, `data | <file>#<key>` in markdown): open
   `data/<file>`, find the fact (and the `[<member>]` of its value, when the key names one), and check the
   claim's value or statement against it. Then check the fact's stored citation, its `source` entry in the
   file's `sources[]`: a `pob-data` citation is re-checked at its pinned `file:line` with a lookup tool, or
   by reading that line of the pinned PoB checkout; an `external` citation has its URL, `accessed` date and
   confidence, and **offline you don't fetch it** (D-232). Check every `data` claim.
3. **`pob-data`** claims: re-check with the lookup tools (repeat the lookup a lookup ref names; look up
   the fact a pinned `file:line` ref states): **all** of them in endgame sections, and **at least 1 in 5
   elsewhere** (rounded up), choosing first the ones the guide's numbers rest on (D-179).
4. **`price`** claims (`price:<id>`, `price | <id>`): find the `prices[]` entry the id names in
   `plan.json` (in the dossier, the plan of the concept it concerns) and check the claim's amount,
   currency, date and league against it. An `unavailable` entry is stated as unavailable, with no amount;
   offline, every entry is `unavailable` with note `offline run` (D-164, D-233). V4 has no trade tool: you
   check the claim against the entry, never against the market (D-178).
5. **`pob-computed`** claims: the ref names a field the final record holds, and the claim states its value
   (as the text rounds it). A `pob-computed` number on a mechanic PoB doesn't apply (step "What PoB
   applies") is a finding: it belongs in the ledger (D-106).
6. **`external-unavailable`** claims: one finding each, `issue` exactly `tagged external-unavailable` and
   `location` the claim's (`stages[<i>].claims[<k>]` or `<file> [^<id>]`): status `accepted-offline` when
   the run log's mode is `offline`, `unresolved` otherwise (C-30). Nothing else is ever
   `accepted-offline`: the workflow and the run checker refuse it on any other finding, and from any other
   lens.
7. **Coverage** `{external, opened, data, dataChecked, pobDataEndgame, recheckedEndgame, pobDataOther,
   recheckedOther, prices, matched}`: the five totals (`external`, `data`, `pobDataEndgame`,
   `pobDataOther`, `prices`) are your counts of those kinds, equal to the run checker's; `opened` is
   `external` online and 0 offline; `dataChecked` equals `data`; `recheckedEndgame` equals
   `pobDataEndgame`; `recheckedOther` is at least `pobDataOther / 5`, rounded up; `matched` counts the
   price claims that agree with their entries.

## Lens `prose`: what the guide says is supported (D-122, D-164, D-219, D-234)

Read `guide.md` section by section, against the guide template's sections (slice 03 §8):

1. **Mechanics claims.** Each statement of how a skill, support, keystone, ascendancy node or item works
   is supported by the source its marker cites: open the cited dossier entry, data fact or record field,
   and re-check a `pob-data` one with a lookup. A claim its sources don't support, or one that contradicts
   what PoB applies (a partly parsed line counted as working), is a finding.
2. **The rolled skill is the main damage source** (D-122): `Summary` and `Rotation` say so, and the
   numbers they cite agree (its figure is the largest of its role in each endgame stage). When it is the
   single-target skill rather than the clear skill, `Rotation` says why (D-148).
3. **Budget statements** (D-164, D-219): the budget variant's total is set against 20 divines; above 20
   and at most 22 its `Checks` say "near the ceiling" in those words; any `unavailable` price means the
   guide says the prices are unavailable and why, and never claims the variant is under 20 divines. The
   non-budget total is set against the ~200-divine reference, never as a cap (D-117).
4. **The survival floor** (D-234): "capped" is said of chaos resistance only when the stage has no
   `chaosResistException`; with one, a single line states the record's chaos resistance and the
   exception's reason.
5. **Offline** (D-201): the first section says the run was offline, that prices are unavailable and that
   no external source was consulted.
6. **Coverage**: an object of your own counts, at least `{sections, mechanicsClaims}`: the H2 sections
   read and the mechanics claims checked.

## Writes

Nothing. You have no write tool: the report is your return, and the skill writes it to
`reports/v4-<lens>-<concept>-p<pass>.json` unchanged (R-5).

## Returns

Your last message is this JSON and nothing after it:

```json
{
  "stage": "V4",
  "lens": "ledger",
  "concept": "c1",
  "pass": 1,
  "mode": "offline",
  "coverage": { "entries": 11, "rederived": 11 },
  "findings": [
    { "id": "v4-ledger-1", "artifact": "plan.json", "location": "ledger[3] (hit_b_fire)",
      "claim": "the waystone-scaled fire hit at area level 79", "issue": "value differs from its facts",
      "evidence": "base 1,234.5 × 1.24 × 24 / 100 = 367.39; the record has 734.78 (the modifier sizes are confidence M)",
      "owner": "D1", "status": "unresolved" }
  ],
  "verdict": "fail"
}
```

- `stage` `"V4"`; `lens` and `pass` from the header; `mode` the run log's.
- `coverage` per lens as above; the `ledger` and `sources` counts must hold up against the run checker's
  own counts.
- `verdict` is `pass` exactly when no finding is `unresolved`. Only the `sources` lens, in an offline run,
  reports `accepted-offline` findings.

## Fault directives

None. The seeded checks FI-4 and FI-5 (AC-W15) are applied by the build coordinator to a copy of a run
folder, not through the skill: a ledger formula wrapped as `(<formula>) * 2` must give the `ledger` lens a
finding naming that entry's `id`, and a copy whose run log says `online` must make every
`external-unavailable` claim `unresolved`.
