# W1: write the guide (`build-guide-writer`)

W1 writes the build's `guide.md`, the reader layer, from the template its plan decides (D-414): the **full
guide**, a game guide a player who has never seen the build follows from level 1 through the campaign to the
endgame (D-101), about 2,840 words; or, for a plan with no campaign stage, the **endgame guide**, the rungs only,
about 2,100 words, for a player who levels with any build of the class and switches to this one. Everything in it
comes from the run's artifacts: the plan, the final compile record, the card and its row of the dossier, the run
log, the D1 gate's verdict file and the rendered `audit.md`. The guide renders the plan: you add no fact or number
of your own (D-276). `audit.md`, the audit layer no player is expected to read, is rendered by the runner with
`scripts/render-audit.mjs` after the final compile (D-355): you copy each endgame rung's Checks block from it,
and write in it only the accepted gate findings' rows under its `Known issues`. V4 checks the plan's hinge
claims, and reads the guide like an editor, after you.

## The build's folder, the template and your mode (D-412, D-414, D-415)

- **The build's folder.** A run holds one folder per finalized card, the header's `buildFolder` under
  `runFolder`: `builds/<id>`, or `.` for a run migrated from schema 3, whose build stayed at the root (D-412). The
  build's files are there: `plan.json`, `compile-record.json`, `audit.md` and the `guide.md` you write, at
  `<buildFolder>/guide.md`. Below, a bare path to one of them is in the build's folder. The run's own files are at
  the run folder's root: `run-log.json`, `cards/`, `dossier.md`, `interviews/` and the gate verdicts under
  `reports/gates/`.
- **The template, from the plan** (D-414), as the run checker decides it: a plan with no campaign stage (every
  stage has a `variant`) gets the endgame guide, `.claude/skills/build-guide/templates/guide-endgame-template.md`;
  any other plan the full guide, `.claude/skills/build-guide/templates/guide-template.md`. Tell them apart
  without reading the plan whole: Grep `plan.json` for `"loadoutName"` (one hit per stage) and for `"variant":`
  (one per endgame stage); equal counts mean no campaign stage. The run log's `builds[]` entry records the choice
  in its `guide` field (`endgame` or `full`), and the checker fails a guide whose H2s aren't its template's.
- **Your mode**, from the build's folder and the plan:
  - **a first pass**, when the folder holds no `guide.md` (or a re-run's `findings` says an earlier attempt
    returned without its files): write it whole from the template the plan decides. A
    `file-only` build's campaign (D-415) is a first pass too: it has no guide yet, and its plan now has campaign
    stages, so you write the full guide;
  - **the fix round or a revision**, when the header carries `findings` or `changed` for a guide that is its
    template's: patch it in place (below);
  - **the campaign mode** (D-415), when the plan has a campaign stage but the folder's `guide.md` is still the
    endgame guide (it has the H2 `Switching over`): rewrite it with the full template ("The campaign mode",
    below).

## Inputs

- **Header:** `stage: "W1"`, `attempt`, `concept`, `mode`, `runFolder`, `runFolderRel`, `buildFolder` (D-412),
  `compile: "none"`, `writes: ["<buildFolder>/guide.md", "<buildFolder>/audit.md"]` (paths from `runFolder`),
  and:
  - `findings`: on a re-run, a note that an earlier attempt returned without its files (they may hold its
    partial work: write them whole); in the fix round, the V4 findings routed to this step; after a revision,
    the user's requests (`code: "user-request"`);
  - `changed`, in the fix round or a revision: the locations D1 and D2 changed, or `"all"` when a gate
    re-ran (an owner recompiled, so the record, the import code and the rendered `audit.md` are new);
  - `accepted`: gate findings the user accepted at an escalation. Each goes under `Known issues`, in both files.
- **Prompt:** the D1 gate's last verdict file, `reports/gates/D1-gate-<concept>-a<n>.json` (the named damage
  source's figures in `basis.rolledSkill`, the market the prices were seen in, `basis.budget.market`, its
  floor, budget and `rolledSkill` findings, `over-target` among them, and on `n` its design field's `toughness`:
  the `warning` and the `ailmentCut`, D-449), and whether the league couldn't be verified.
- **The fix round and revisions** (D-264). You never write the guide anew: fix it in place with Edit (the
  campaign mode, below, is the one exception, D-415). Fix
  every place each of your findings touches, not only the flagged location. Then patch every place the guide
  renders a claim at a `changed` location, so it says what the plan now says. With `changed: "all"`, also copy
  the new record's `importCode` into `Your PoB file`, copy each rung's Checks block again from the re-rendered
  `audit.md`, and bring every number the guide quotes, the verdict lines' included, up to the current record
  and plan. A `hinge: no` finding is fixed by removing or narrowing the sentence. The re-check reads what you
  changed. Leave the lines under the guide's `### Known issues` and the rows of `audit.md`'s `Known issues` to
  the runner's step 14, which replaces them whole, except to add a gate finding newly in `accepted`.
- **Read**, the independent reads in one response; each large file by part, never whole:
  - the template the plan decides (above): `.claude/skills/build-guide/templates/guide-template.md` or
    `.claude/skills/build-guide/templates/guide-endgame-template.md`;
  - `plan.json` (it can pass 90K tokens) by the fields you need, never whole and never stage by stage: you have
    no `mcp__pob2__guide_run` view (your tools are file tools only, D-257), so Grep each field with line numbers
    and Read from the hit to its closing bracket: `"claims"` (each `{id, text, kind, source}`; the path claims
    name each campaign stage's tree path, and a `reason` claim on `m` names the ascendancy's nodes in the order to
    take them, with why, D-413), `"groups"` (supports in order, `count`, `countReason`), `"slots"`
    (the item texts, in upgrade order), `"anoint"`, `"respec"`, `"chaosResistException"`, `"scenario"` (the
    reward picks), `"customMods"`, `"loadoutName"`, `"league"`, `"versions"`, `"ledger"` and `"prices"`. Never
    Read a `tree` object or its `nodes` id lists: the path claims and the respec's `note` carry what the guide
    says, and the ascendancy's nodes come from their order's claim, never from `ascendancyNodes` (D-413);
  - `compile-record.json`, the final compile's record (C-33), by Grep: each stage's `loadoutName`, `level`,
    `outputs` (`Life`, the four resistances, each `<Type>MaximumHitTaken`, `TotalEHP`), `outputsSet2`'s `Life` on a
    stage that uses weapon set 2 (rule 10), the Count-scaled
    `countedSkillOutputs`, `configWritten` (the reference hits, `enemy<Type>Damage`), `computedWithCustomMods`,
    `measures` (`damage {map, resisting, boss}`, `cull`, `trigger`, `dps`, `ehp`, `arbiter` with its `rows` and
    `avoid`, `toughness`, `clearSpeed`), `treeChange` (`{from, refunded, added}` on a schema-8 plan's stage with a
    stage before it, D-452), `anoint` (the
    notable and its recipe) and, for the endgame guide, `m`'s `requirements` (`{level, by[]}`: the level the build works from, and the items
    `{kind: "item", name, slot}` and gems `{kind: "gem", name, group, gemLevel}` that set it, D-413); and `engine`,
    `pobFile`, `importCode`, `versionNotes`, `loadoutWarnings` and `saveWarnings`;
  - `audit.md`, the runner's render: Grep `^#` and Read its `## Checks` section (one H3 per endgame rung,
    titled with its loadout name), its `## Estimates` table (each ledger entry's value, the plan's current
    formula over the record: a `boss_<stage>` estimate's among them) and its `## Known issues` heading's line;
  - the card `cards/<id>.md` (its class, chain, enabler, traps and estimates), its row of `dossier.md` (Grep
    `^| <id> |`: its damage kinds and pieces, no figure, D-436), and `run-log.json` (the mode and the date);
  - the C1/E1 facts under `data/` that a claim cites, by key;
  - the gates' interview notes, `interviews/<gate>-<visit>.md` (Glob `interviews/*.md`), for the FAQ.

## Work: the guide

Write `guide.md` from its template, section by section (the template gives each section's word budget). The
run checker holds the guide to rules 1 to 4 and to the Checks blocks; V4 reads it against the rest.

1. **Headings.** One H1 naming the roll (`<Ascendancy> / <Skill>: <concept title>`), then exactly the
   template's H2s, the full guide's fourteen or the endgame guide's twelve, in its order, and no other H2. Under
   `Leveling` (the full guide), one H3 per campaign stage (a
   stage without `variant`), in plan order, titled with its loadout name **exactly** as the record's
   `stages.<id>.loadoutName` has it, and no other H3. Each `Endgame` H2 has its H3 `Checks`; `What PoB can't
   show` ends with the H3 `Known issues`. The H1's title says what the final build does, from the final plan, never a
   card hook the final plan no longer carries.
2. **The cap.** At most 3,000 words, the H1, the import code and the Known issues list not counted (D-283).
   Aim at the template's budgets, about 2,840 in all. The endgame guide's cap is **at most 2,300 words**, counted
   the same way, and its budgets are about 2,100 in all (D-414).
3. **No pipeline text** (D-276). No footnote markers (`[^…]`), no confidence labels ("confidence L"), no
   finding ids, no pipeline words (lens, finding, owner, claim, location) and no stage ids outside the
   loadout names. The plan's claims carry the guide's sources; `audit.md` keeps the confidence. Nor any note
   about the pipeline or the run ("unconfirmed offline", "the card's hook", a raw multiplier such as "1.251×").
4. **The verdict lines** (D-283, D-353). `Survival by stage` has a one-line legend and one line per endgame
   rung in the template's fixed form, word for word but the placeholders, and no campaign line (D-354). The
   run checker compares each number with the record:
   - the level is the stage's `level`; the resistances are the record's `FireResist`, `ColdResist`,
     `LightningResist` and `ChaosResist` at −60%;
   - "Max hit <n> physical against about <hit>": the record's `PhysicalMaximumHitTaken`, against the stage's
     `enemyPhysicalDamage` in `configWritten`, the reference hit the compiler wrote;
   - "at least <n> elemental or chaos against about <hit>": the least of the four other
     `<Type>MaximumHitTaken`, against the largest of the stage's other four `enemy<Type>Damage` in
     `configWritten`;
   - "<Skill> about <map> DPS against map monsters, about <resisting> against resisting rares, about <boss>
     against a Pinnacle boss" (D-437, D-447, D-454): the named damage source's damage figure, the record's
     `measures.damage.map` (with its cull when the rung states `skills.cull`), never PoB's Full DPS; the same
     figure against the map enemy with 40% fire, cold and lightning resistance, `measures.damage.resisting`; and the
     rung's boss figure, the `boss_<stage>` ledger value when the plan has that entry (audit.md's Estimates row),
     else `measures.damage.boss`. The run checker compares each with the same value. A record with no
     `damage.resisting` (compiled before amendment 12) keeps the two figures, "<Skill> about <map> DPS against map
     monsters, about <boss> against a Pinnacle boss."; one with no `measures.damage` (compiled before amendment
     11) the one-figure form, "<Skill> about <n> DPS.", its `measures.dps` (D-294);
   - "Effective HP about <n>.", which ends the line: the stage's `measures.ehp`, its `TotalEHP` (D-294).

   Round each number as a guide does, at its last significant digit: 2,736 is "2,740" or "2,700", 401.996 is
   "about 400", a hit of 439 "about 440". **The label** (D-353, D-459): on `b` and `n` it follows the record's
   `measures.arbiter`, never your judgment, read by its **deciding row** (the rung's one-shot row with the lowest
   `hitsSurvived`, else its row with the largest ratio) against the floor, `arbiter.hitsSurvivedFloor` in
   `.claude/skills/build-guide/references/toughness-targets.json` (0.8), in one of three forms, `<x>` the row's
   `hitsSurvived` rounded down to a whole percent (79.6 is 79) and `<type>` its type, a mixed hit's types joined by
   " and ":
   - **"survives the Arbiter's hits"**, when the deciding row survives the full hit;
   - **"survives <x>% of the Arbiter's <type> hits, by evading or deflecting them"**, when it is one-shot by the
     full hit but survives at least 80% of those hits;
   - **"one-shot by the Arbiter's <type> hit"**, under the floor, with **" (it survives <x>% of them)"** after it
     when x is above 0 ("one-shot by the Arbiter's physical hit (it survives 79% of them)").

   The checks use the unrounded value: 79.6% is under the floor though you write 79. A record whose rows carry no
   `hitsSurvived` (compiled before amendment 12) keeps the two older forms: "survives the Arbiter's hits", or
   "one-shot by the Arbiter's <the worst hit>", `measures.arbiter.worst`'s `type` then "hit". A row with no verdict
   (PoB gave it no max hit), on a rung that isn't one-shot, is "not measured against the Arbiter", and a gap in your
   return. On `m`, which faces no Arbiter, the label (`solid`, `watch`, `risky`) is your judgment of its line's
   numbers.
5. **Facts and advice** (D-276). A fact is a plain statement of something the plan or the record holds, and
   numbers come from them, rounded as above. Advice is in the first person ("I drop Herald of Ash first", "my
   upgrade order"): that is its label, and it isn't verified, but a number inside it is still the plan's or
   the record's, and it never asserts a fact the plan lacks.
6. **Each caveat once** (D-279, D-351). A caveat the build hinges on (a source of confidence M or L, a
   disputed fact, a judgment, a mechanic no lookup confirmed, what PoB doesn't model) appears once, where the
   reader acts on it, usually in `What PoB can't show` by the figure it qualifies. A later mention doesn't hedge
   it again, and never states it as settled. A minor caveat is cut, not hedged. State a mechanic as reliable
   only when the build has a source for it.
7. **Not a tutorial** (D-280). A sentence that explains how the game or PoB works stays only when it names
   something this build uses, needs or avoids (its skill, supports, nodes, key items, an attribute or level
   requirement, or a plan number) and it changes what the reader does with this build. The swap test: if the
   sentence would read as true and useful, word for word, in a guide for another skill on another class, cut
   it. Keep the consequence, not the rule ("Blood Hunt needs a level-7 uncut gem", not how uncut gems work).
   Campaign practicals are actions, not explanations.
8. **Your PoB file.** The import code goes in this section's first fenced block, copied character for
   character from the record's `importCode` (D-205). Then the file name; the loadouts as one ordered line,
   each with its trigger (the endgame guide's: the three rungs only); that the items are stat examples; the
   engine version (the record's `engine` and the plan's `enginePatch`) and the boss data's patch
   (`externalPatch`); in an offline run, that it was made
   offline and no price was checked (the word "offline" must appear here). **The pricing line**, once, online
   (D-374): the league and the date the prices were seen, with the league day (`basis.budget.market.day`; when
   it is `null`, that the day is unknown); that early endgame (entering maps and budget) is estimated at about
   day 7 of a league and late endgame (non-budget) at about day 21; when the day is under 21, that the prices
   are from an early market; that trade moves a lot; and that the build can be re-priced with the skill at any
   time. **The league** is `plan.json`'s
   `league`: `unverified` there means trade was unreachable when the endgame was priced, and the guide says
   the league couldn't be verified. Then the record's PoB-file notes, each once, in plain words:
   `versionNotes`; `loadoutWarnings` (PoB2's loadout switch can drop an off-hand that Giant's Blood,
   Instruments of Power or Lord of the Wilds makes legal: tell the reader to check Weapon 2 and Weapon 2 Swap
   after switching and re-equip it); `saveWarnings` (saving in PoB2 drops some config options: set them
   again). **The comment lines** (D-469), on a schema-9 plan with custom modifiers: one line saying that the
   lines starting with `#` in PoB's Configuration tab show in red, PoB's colour for a line it doesn't apply, and
   that they are the custom modifiers' notes, there on purpose.
9. **Leveling** (the full guide; D-354; at most 110 words a stage), per campaign stage: the setup, its skill
   with its supports in the order the group lists them; the tree path, the notables and keystones the stage's path
   claim names, in its order; attributes (have and need); gear in my upgrade order, the stage's changed slots
   in `items.slots` order, each with the build-specific mods its item text holds, as mods to buy on trade; the
   target life, the record's `Life` for the stage; when to swap; on a schema-8 plan, **the tree-change line**
   (rule 10) when the stage's `treeChange.refunded` is above 0; on a schema-7 plan, any respec, with the change
   its `note` names and its gold cost (D-144, D-438). No
   resistance, max hit or EHP before the endgame, and no crafting step: the reader buys gear on trade (D-348).
   **Campaign route and rewards** (D-265, D-283): the reward quests in route order. For each reward choice the
   plan picks (a stage's `config.scenario` entry citing `campaign/progress.json#q.<key>.options[<i>]`), name
   the quest, then the picked option by its first line exactly as the fact lists it (the run checker looks
   for it there), then the reason the plan's claim gives. Never list a choice's options without its pick.

   **Switching over** (the endgame guide only, D-413, D-414; about 250 words) takes the place of Leveling,
   Campaign route and rewards, and Gem and ascendancy timing, and says four things, in this order:
   - **When the build works:** level with any build of the class (the card's `Class`); the build works from
     level `m`'s `requirements.level` in the record, because of what sets it, its `requirements.by[]`, in plain
     words: an item by its name and slot, a gem by its name and gem level. Never a level of your own.
   - **The ascendancy and the order to take its nodes:** the nodes as the plan's `reason` claim on `m` names
     them, in its order, with the reason it gives. You read no node ids: with no such claim, write the
     ascendancy alone and report the gap.
   - **Each campaign reward pick the plan makes** (D-413): for an endgame-only build D1 makes them, the same
     pick on every rung, as a `config.scenario` entry citing `campaign/progress.json#q.<key>.options[<i>]`. Name
     the quest, then the picked option by its first line exactly as `data/campaign/progress.json` lists it (the
     run checker looks for it in this section), then the reason the plan's claim gives. Never list a choice's
     options without its pick.
   - **A respec, or a player switching from a levelling build:** the PoB file holds the whole tree for each
     rung; refund what the rung doesn't use. Say once, here, that the gold cost isn't computed, since it
     depends on the tree the reader brings; give no gold figure for the switch. (A rung's own change from the
     rung before it is its tree-change line, in its Endgame section, rule 10; on a schema-7 plan, its respec with
     its gold cost.)
10. **The endgame rungs** (D-281). `Endgame: entering maps` is stage `m`, `Endgame: budget` stage `b`,
    `Endgame: non-budget` stage `n`. Each H2 opens with its one "Move here when" line. Entering maps gives the
    changes from the Epilogue (in the endgame guide, which has no Epilogue, what the loadout holds when the
    reader switches to it) and D1's numbered buy order toward its 5-divine target; budget its buy order, a
    slot table and the gems and tree with their reasons; non-budget its upgrade order. **The slot table**
    (D-374), one row per rare: its required affixes with their minimums, as text, as what to buy (the price
    entry's `query.required`); the rest of its affixes as the priority after them; and for an over-target slot
    (an `over-target` finding), its fallback (the `<id>-fallback` entry's required affixes, and its price as the
    Checks block's "Over target" sentence gives it, a range at the rung's price day) beside them, said to be
    unmeasured. Where the plan's claim names an affix's source that limits the base, the required affixes say
    so. **The tree-change line** (D-452), on a schema-8 plan's stage whose record carries `treeChange` with
    `refunded` above 0: exactly `Respec: refund <refunded> points and allocate <added>; respeccing costs gold.`,
    the counts the record's, no gold figure (no source gives one, A-32) and no node names (the PoB file holds each
    rung's tree); none when `refunded` is 0. The run checker compares the counts. On a schema-7 plan, where a stage
    has a `respec` (from the rung before it on the ladder, D-282), a respec line gives the dropped nodes and the
    gold cost, after the change its `note` names: the rung's scaling changed (D-438).
    - **The anoint** (D-358). On `b` and `n`, one line names the stage's `items.anoint` notable, its recipe of
      three Distilled Emotions as the record's `anoint` names them, its price (the `b-anoint` or `n-anoint`
      entry, or unavailable) and the plan's `reason`. `m` has no anoint: when `b` has one, one line tells a
      player who can afford it before maps to anoint the amulet with `b`'s notable. A price you write names
      its currency in players' words, "exalts", "divines" or "chaos", never the trade id `exalted` (D-442).
    - **A weapon swap's Life cost** (D-426). On a rung whose record stage has `outputsSet2` (the stage uses weapon
      set 2, measured with it active), compare its `Life` with the stage's `outputs.Life`. When set 2's is lower,
      because set 2's tree or items hold less, the rung's section says once what the swap costs: your Life falls from
      about <`outputs.Life`> to about <`outputsSet2.Life`> while set 2 is out (the template's `Weapon swap` line).
      With no `outputsSet2`, or no lower Life on set 2, leave the line out.
    - **The pinned weapon** (D-464). Where a rung's Swap slot holds its set-1 weapon (`items.slots[]` with
      `sameAs`), one line where the gear names it: pin the weapon to both weapon sets, one item held in both.
    - **The flasks** (D-472), one line, once, in the first endgame rung: the two flasks' bases (`Flask 1`, `Flask
      2`), kept on every rung, their lines not mattering unless the build uses a flask effect (then the lines that
      keep its uptime); with no mana flask, why (its claim).
    - **Corruption** (D-471), the user's one exception to D-348: for each corrupted unique on `b` or `n` (an
      `{enchant}` line beside a `Corrupted` line in its item text, the amulet's anoint aside), one line holding the
      unique's name, "buy several" and "corrupt", "Buy several <unique> and corrupt them until one rolls <line>",
      with why the budget doesn't count it (it's cheap uncorrupted); for each skill gem with `"corrupt":
      "plus_one_level"`, one line holding the gem's name, "corrupt" and "+1 level", "Corrupt cheap low-level <gem>
      gems until one gets +1 level, then level it to 20". The run checker looks for each. A unique that drops
      corrupted (Split Personality) needs no line.
    - **Checks** (D-355). Each rung's `### Checks` holds that rung's block from `audit.md`'s `## Checks`, the H3
      titled with its loadout name, copied verbatim: every line under that H3 to the next heading, and nothing
      else. The render already holds the chaos exception line (D-234), the budget line with its range, price
      day and target, and the over-target slots on `b` and `n` (D-164, D-374), the Arbiter verdict on `b` and
      `n`, and the rough clear speed and movement speed; don't restate or reword them. The run checker fails a
      Checks block that differs from the render.
11. **How to play it**: clear and single target; the named damage source as the main damage (D-122), and why
    when it isn't the clear skill (D-148). For a minion skill, say that the player commands the minion and the
    minion deals the damage (D-379). **One line naming the first thing to change if the build stalls** (D-459),
    always: the lever, piece or defence the plan's claims and trades point to first ("If maps start to stall, I
    take the budget rung's deflection trade first"). One optional line on defence the gate can't see, where the
    build has it: dodge timing, flasks, a recharge delay, stun risk, blind upkeep. No kill time and no hits to kill
    (D-353).
12. **What PoB can't show**: each caveat the build hinges on, once, by the figure it qualifies (D-351), and the
    settings the headline figures assume, from the plan's config (charges, stacks, counts). **The boss figure**
    (D-447): when the plan estimates it (`boss_<stage>`), say once that it is my estimate from the rotation, what
    it corrects (the entry's claim, in plain words) and PoB's own figure beside it. **A triggered skill**
    (D-437): when the record's `measures.trigger` is set, say once that PoB rates <the skill> at its hand-cast
    speed and doesn't model <the meta gem>'s Energy. **The defence lines** (D-459), each once and only when it
    applies: the design gate's warning, in plain words (the D1 gate's design field's `toughness.warning` on `n`:
    the EHP reads fine, but the Arbiter's <type> hit one-shots the build, or with every condition against it the EHP
    falls under its band, and the fix family it names); for a deflecting build, what deflection does (a big hit
    that gets past evasion loses its deflected share, 40% at base, most of the time, which PoB's max hit ignores)
    and its average cut to ailment damage from hits (the field's `ailmentCut`, which PoB doesn't apply, PG-97); and
    when the defence leans on recoup, regeneration, leech or recharge, that Effective HP leaves them out by PoB's
    design. Each Count above 1
    and each custom modifier, with the reason the plan gives it (`countReason`, `customMods[].reason`),
    rendered from the plan (D-294): the figures they touch are estimates (D-296). **Support sockets** (D-359):
    when a skill a passive grants (the tree or the ascendancy) holds supports, say once, here, that its
    support count is an estimate: 3 below level 40, 4 from 40, 5 from 60. Never tell the reader to save or use
    Jeweller's Orbs for it: they add sockets to items only. Its last part is always the H3 `Known issues` (see
    "Known issues" below).
13. **FAQ**: 3–5 questions a player asks. The user's gate questions that a reader of the guide would ask too are

## Known issues (D-265, D-276)

The guide's `### Known issues` lists plain sentences, one per line, with no id: each says what is wrong in the
guide and what is true instead, with no pipeline words and no JSON paths. `audit.md`'s `Known issues` table
holds each one's row: `| <id> | <lens or gate> | <stage> | <the sentence the guide prints> |`.

- You write each accepted gate finding: its sentence in the guide, and its row in `audit.md`, with its code
  as the id, its gate (`D1-gate` or `D2-gate`) and its plan stage. In `audit.md`, replace the render's
  `None.` under `## Known issues` with the table head (`| Id | Lens or gate | Stage | Sentence in the guide |`
  and its `|---|---|---|---|` line) and your rows:
  `- The budget variant spends more passive points than level 90 allows, so PoB2 shows it over the limit.` and
  `| level-points | D1-gate | b | The budget variant spends more passive points than level 90 allows, so PoB2 shows it over the limit. |`.
  With none, the guide's list holds the one line `None.`, and `audit.md`'s stays as rendered.
- The runner adds each V4 finding left open after the re-check: the verifier's `reader` sentence word for word
  in the guide, and its row `| <id> | V4 | — | <reader> |` in `audit.md` (SKILL.md step 14).

The runner finds both lists by the line numbers you return, so return them after your first write and after
every patch, as the lines of the headings in the files as you leave them.

## The campaign mode (D-415)

The user asked for the campaign of a `completed` build, which has the endgame guide (the final gate's
`campaign`, or `campaign:<id>` after a resume). Before you run, the runner made the round copy, D2 added the
campaign stages to the plan, keeping D1's reward picks, the D2 gate re-ran the final compile (a new record,
import code and PoB file), and the runner re-rendered `audit.md`. You are in this mode when the plan has a
campaign stage and the build's `guide.md` is still the endgame guide (it has the H2 `Switching over`). **This is
the one case where you write the guide anew outside a first pass:** it amends "You never write the guide anew"
above for this mode only.

1. **Write `guide.md` whole, with Write,** from the full template,
   `.claude/skills/build-guide/templates/guide-template.md`: its fourteen H2s, its 3,000-word cap and its
   budgets, held to every rule of "Work: the guide".
2. **Keep the endgame sections' text where the plan didn't change them.** At a glance, Survival by stage,
   Priorities, the three `Endgame` H2s, How to play it, What PoB can't show and the FAQ come over from the
   endgame guide as they stand, except where they render something that changed: bring every number up to the
   new record (the verdict lines' included), copy each rung's Checks block again from the re-rendered
   `audit.md`, and rewrite a sentence only where the claim or field it renders now says something else.
   Entering maps now opens with the changes from the Epilogue, as the full template has it.
3. **Write the campaign's sections** as a first pass does: Gem and ascendancy timing (the trials, and the
   ascendancy's nodes in the order the plan's claim names them, which Switching over gave), Leveling (one H3 per
   campaign stage, rule 9) and Campaign route and rewards (every reward pick, D1's kept, by its option's first
   line: a full guide names them here, where the run checker looks).
4. **Your PoB file:** the new record's `importCode`, copied again, its PoB file name, and the loadouts line
   with the campaign's loadouts before the rungs.
5. **Switching over goes.** A guide that levels the reader has no place for its level line or its respec
   advice; its ascendancy order and its reward picks have moved to the sections of step 3.
6. **Known issues** as a first pass writes them: the accepted gate findings' sentences in the guide, or `None.`,
   and their rows in the re-rendered `audit.md`. The runner's step 14 adds the open findings after the
   campaign's V4 pass and re-check.
7. **Changelog:** keep the endgame guide's entry, and add one dated entry for the campaign.

Return as on a first write. A `file-only` build's campaign isn't this mode: it has no guide yet, so you write
the full guide in a first pass.

## Writes

`guide.md`, and in `audit.md` only its `Known issues` lines; no other file: no notes, drafts or scratch files,
in the run folder or anywhere else. Both are in the build's folder, `<buildFolder>/`. Write `guide.md` with Write;
to correct it afterwards, fix it in place with Edit rather than writing it again (D-257), except in the campaign
mode, which writes it again with Write once (D-415). Change `audit.md` only with Edit, and only under
`## Known issues`: the rest is the render's. You can't change the plan, the record or the dossier: if one looks
wrong, write what it says and report the problem in `gaps`.
