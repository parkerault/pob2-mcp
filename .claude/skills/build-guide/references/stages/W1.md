# W1: write the guide (`build-guide-writer`)

Slice 03 §5.3 step 5 and §8; spine C-30, D-101, D-105, D-106, D-122, D-164, D-205, D-219, D-234. W1 writes
`guide.md`: the guide a player who has never seen the build follows from level 1 through the campaign to
an endgame variant (D-101). Everything in it comes from the run's artifacts: the plan, the final compile
record (its ledger values included), the dossier and the D1 gate's verdict the prompt gives. You add
explanation; you never add a number of your own. V3 and V4 check the guide after you.

## Inputs

- **Header:** `stage: "W1"`, `attempt`, `concept`, `mode`, `runFolder`, `runFolderRel`, `compile: "none"`,
  `writes: ["guide.md"]`, and:
  - `findings`: on a re-run, a `null-result` note (an earlier attempt returned nothing, and `guide.md` may
    hold its partial work: write it whole); on a guided retry, the user's guidance (`code:
    "user-guidance"`); after a routed V3/V4 finding or a revision request, what to change;
  - `accepted`: findings the user accepted at an escalation. Each goes under `Accepted failures`.
- **Prompt:** the D1 gate's last verdict (its budget totals and rates, and its floor, budget and
  rolled-skill findings), and whether the league couldn't be verified. When the workflow resumed past D1
  and ran no D1 gate, the prompt says so: read the highest-numbered
  `reports/gates/D1-gate-<concept>-a<n>.json` instead.
- **Read:**
  - the template `.claude/skills/build-guide/templates/guide-template.md`;
  - `plan.json` (stages, `claims`, `ledger`, `prices`, `versions`, `league`, every `chaosResistException`
    and `respec`);
  - `compile-record.json`, the final compile's record (C-33): each stage's `loadoutName`, `level`,
    `outputs` and `skillOutputs`, the `ledger` values, `engine`, `pobFile`, `importCode`, `savedLevel`,
    `versionNotes`, `loadoutWarnings` and `saveWarnings`;
  - `dossier.md` (the concept's entry, the mechanics) and `run-log.json` (the mode, the date, and
    `checkpoints[]`: checkpoint 1's entry that picked this concept, which is the only record of why it was
    picked; the dossier is written before checkpoint 1 and doesn't say);
  - the C1/E1 facts under `data/` that a claim cites;
  - `.claude/skills/build-guide/references/source-markers.md`.

## Work

Write `guide.md` from the template, section by section (`guide-template.md` has the shape; §8 says what
each section must contain). The rules the run checker holds the guide to:

1. **Headings.** One H1 naming the roll (`<Ascendancy> / <Skill>`), then exactly the template's thirteen
   H2s, in its order, and no other H2.
2. **Versions, prices and import code.** The engine data version (the record's `engine` and the plan's
   `enginePatch`) and, separately, the patch of the prices and boss data (`externalPatch`); the date; the
   league (offline: none; unverified when the prompt says so); the mode, and in an offline run that prices
   are unavailable and no external source was consulted (the word "offline" must appear here); the PoB file
   name; that each stage is a loadout and the file is in auto-level mode. **The import code** goes in this
   section's first fenced block, copied character for character from the record's `importCode` (D-205).
   **The league** is `plan.json`'s `league`: `unverified` there means trade was unreachable when the
   endgame was priced, and the guide says the league couldn't be verified (so does the prompt when D1
   reported it).
   Then the record's PoB-file notes, each in plain words, wherever the record has them:
   - `versionNotes`: where the engine differs from what the plan was written against;
   - `loadoutWarnings`: PoB2's loadout switch can drop an off-hand that Giant's Blood, Instruments of Power
     or Lord of the Wilds makes legal; tell the reader to check Weapon 2 and Weapon 2 Swap after switching
     and re-equip the off-hand;
   - `saveWarnings`: saving the file in PoB2 drops some config options from the named stages; tell the
     reader to set them again after saving.
   Repeat the two warnings as hard warnings in `FAQ and common mistakes`.
3. **Leveling.** One H3 per campaign stage (a stage without `variant`), in plan order, titled with its
   loadout name **exactly** as the record's `stages.<id>.loadoutName` has it, and no other H3 under
   Leveling. Each gives the level range, skills and supports with socket counts, the tree points to add,
   any respec with its gold cost (D-144), the ascendancy pick, gear with a dated price or `unavailable`,
   the swap trigger, and the stage's PoB numbers from the record.
4. **The endgame variants.** `Endgame: budget variant` is stage `b`, `Endgame: non-budget variant` stage
   `n`: gear by slot with dated prices (a `price` marker per entry), stat priorities, gem links with gem
   levels, the tree, the character level and ascendancy points (D-193), and the earned config with each
   producer and uptime (D-114). When the variant's stage has a `respec` (the respec from the last campaign
   stage into the variant, D-144), a "Respec from the campaign" line lists the dropped nodes and the gold
   cost, with the cost's marker. Each has an H3 `Checks`:
   - **the survival floor**: all four resistances from the record, at the −60% penalty; say "capped"
     of chaos only when it is (no `chaosResistException`). When the stage (`b` or `n`) has a
     `chaosResistException`, **one line** holds both the record's `ChaosResist` for that stage, as
     a number with `%`, and the exception's `reason` copied in full, word for word: "Chaos resistance stays
     at 28% because no slot can carry chaos resistance without dropping a core item or breaking the
     budget." Don't wrap that line (D-234);
   - **max hit taken** against each reference hit of the stage's scenario, named as what it is: the
     waystone-scaled hit (the area level's monster damage at the top of each waystone damage modifier's
     range, D-254), physical and each element, each with the marker of its ledger entry
     (`ledger | hit_<stage id>_<type>`). Quote the hit as that entry's value in the record's `ledger`
     (438.55), not the scenario's whole number (439), which is that value rounded up for PoB (D-256);
   - **the budget** (D-164, D-219), from the prompt's D1 gate verdict: the total against 20 divines. When
     the total is over 20 and at most 22, the budget `Checks` say **near the ceiling**, in those words.
     When any price is `unavailable`, say the prices are unavailable and why, and that the variant can't be
     claimed to be under 20 divines; never claim it is. The non-budget total is set against the ~200-divine
     reference, never as a cap (D-117), and the non-budget section adds the upgrade order from the budget
     variant;
   - **the Arbiter of Divinity** (D-116, A-30): its hits against max hit taken, and the time-to-kill range
     from the ledger, confidence L; **the mapping signals** (D-121, D-132), with their confidence.
5. **The rolled skill is the main damage source** (D-122): Summary and Rotation say so. When it is the
   single-target skill rather than the clear skill, Rotation says why (D-148). **Why this concept**, in
   Summary, comes from `run-log.json`'s checkpoint 1 entry whose `answer` picked it: who answered
   (`answeredBy`) and the user's own words when the answer holds any. A `pre-supplied` or `default` answer
   (a test config) picked it by rule: say so and give no reason. Never invent one.
6. **How it works** gives the mechanics with sources and the ledger summary: each entry's claim, its
   value from the record's `ledger`, and its formula in words (D-106).
7. **Confidence and what PoB can't model**: `check_model_coverage`'s flags from the dossier and plan, the
   hand calculations, the M and L inputs (A-29); offline, the `external-unavailable` claims. **When the
   header's `accepted` holds findings**, an H3 `Accepted failures` lists each on its own line: its `code`
   (or a V3/V4 finding's `id`) in backticks, its `gate` (`D1-gate`, `D2-gate`, `V3`, `V4`) and its plan
   stage, then the message. Without accepted findings, there is no such H3.
8. **Changelog**: one dated entry for this version.
9. **Markers** (`source-markers.md`). Every number and game claim carries a footnote marker `[^<id>]`, ids
   `g1`, `g2`, …. Each id has exactly one definition line, and every definition goes under `Sources`, the
   last heading, with nothing after them. A record number cites `pob-computed | <stageId>.<Field>` (or
   `<stageId>.g<group>s<skill>p<statSet>.<Field>`); a ledger value `ledger | <id>`; a price
   `price | <priceId>`, an entry of `plan.json` (a skeleton's prices don't count here); a C1/E1 fact
   `data | <file>#<key>`. Copy a dossier claim's tag with its claim. Offline, a claim that would need an
   external source is `external-unavailable | external source unavailable (offline run) | confidence: <H|M|L>`;
   online, an `external` tag has `accessed` and `confidence`; a `judgment` has `confidence`.

**Keep every hedge.** State a mechanic as reliable only when the build has a source for it (the item,
node or gem that grants it, as the plan or the dossier cites it). A claim that rests on an unconfirmed
mechanic, or on a judgment or input of confidence L, keeps its hedge everywhere the guide repeats it
(Summary, Rotation, the earned config, the FAQ), not only where it is first stated.

Write for a newcomer: plain words, the why behind each choice, numbered steps where order matters.

## Writes

`guide.md` only, and no other file: no notes, drafts or scratch files, in the run folder or anywhere
else. Write the guide with Write; to correct it afterwards, fix it in place with Edit rather than writing
it again (D-257). You can't change the plan, the record or the dossier: if one looks wrong, write what it
says and report the problem in `gaps`.

## Returns

Your last message is this JSON and nothing after it:

```json
{ "file": "guide.md", "importCode": "eNrtWV1v2zYU…", "gaps": [] }
```

- `importCode`: the code you copied into the guide.
- `gaps`: what you couldn't fill and why, one line each (a record field that is missing, a plan claim
  with no source); `[]` when none.

## Fault directives

None.
